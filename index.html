Evidence-Based Diabetes Assistant July 2026 - August 2026

Before writing any code, I spent some time researching how I wanted to approach this project. I came across Pixegami's LangChain RAG tutorial, which provided a great foundation for building a Retrieval-Augmented Generation (RAG) pipeline. Rather than simply recreating the tutorial, I wanted to build something more practical and aligned with my interest in AI for healthcare.

My original idea was to create a general medical chatbot, but I decided to narrow the scope to diabetes. Diabetes has an extensive collection of publicly available clinical guidelines and research, making it an ideal domain for a focused RAG application. I also felt that specializing in a single area would make the project more realistic and applicable. From there, I started brainstorming additional features that could make the application genuinely useful in a clinical setting.

With the project planned out, I set up my development environment by installing the required dependencies, creating a virtual environment, and configuring an OpenAI API key. One lesson I've learned from previous AI projects is the importance of protecting API keys. Early on, I accidentally committed one to GitHub—a mistake every developer hopes to make only once. Since then, I've made it a habit to use environment variables and .gitignore, and it was nice knowing I had set this project up the right way from the beginning.

Today, I focused on gathering high-quality diabetes resources for the RAG pipeline. I searched through several reputable healthcare organizations to find the most up-to-date clinical guidelines and statistics. I ended up selecting reports from the American Diabetes Association (ADA) for the Standards of Care, the CDC for diabetes statistics, and NICE for clinical guidelines. I had hoped to include a report from the WHO as well, but I was surprised to find that their most relevant diabetes publication was from 2016. For now, I decided to start with just a few trusted sources so I could verify that the pipeline worked correctly before expanding the knowledge base.

After downloading the PDFs, I organized them into my data directory and created a JSON file containing metadata for each document, including the organization, source URL, publication year, citation, and other useful information. This took longer than I expected, but having accurate metadata would later allow me to generate proper source citations in the application.

I then created load_documents.py, which loads the PDFs, attaches the metadata to each page, and splits the documents into smaller chunks for embedding and retrieval. During testing, I ran into an issue because the tutorial I was following used an older LangChain package that had since been updated. After a bit of debugging and research, I updated the code to the current API, and everything worked as expected—the documents loaded successfully, the metadata was attached correctly, and the chunks were ready for the next stage of the pipeline.

With the documents loaded, the next step was creating the vector database using Chroma. This was my first time working with Chroma, and I was pleasantly surprised by how straightforward the setup was. Before generating the embeddings, I realized my OpenAI account didn't have any API credits, so I added some, ran a quick test request to verify everything was working, and confirmed the API was responding correctly. Once that was done, I ran my script, and Chroma successfully created the vector database.

Next, I built the RAG pipeline itself. I created a prompt template that instructed the language model to answer questions using only the retrieved context from the database. When a user asks a question, it is converted into an embedding, Chroma retrieves the most relevant document chunks, and those chunks are passed to the model to generate a response.

I chose gpt-4o-mini because it offers an excellent balance between performance and cost, making it a great fit for this project. The initial version of the application was able to answer questions and return useful source information, including the document title, citation, URL, and page number. I did run into one issue where the tutorial used the outdated langchain.prompts package, but after updating it to langchain_core.prompts, everything worked as expected.

To test the pipeline, I asked, "What is the target A1C for most adults with type 2 diabetes?" The model correctly responded that the target A1C is less than 7.0% (53 mmol/mol) and included citations to the supporting guideline. Seeing both an accurate answer and proper source attribution was a satisfying milestone—it showed that the core RAG pipeline was working exactly as intended.

My goal for today's coding session was to have a working version of the application running through Streamlit. Since I had never used Streamlit before, I started by creating a simple chat interface. I was impressed by how quickly it can turn a Python script into a web application with very little frontend code. In app.py, I connected the RAG pipeline from the previous day to a chat-style UI that accepts user questions, displays the model's response, and shows the supporting sources in a collapsible section.

The first time I ran the application, I was greeted with several missing module errors. This was confusing because I had already installed the required packages. After some debugging, I discovered that Streamlit was running from my Anaconda installation instead of my project's virtual environment. Running it with my environment's Python (python -m streamlit) solved the issue, and the application launched successfully.

With the interface working, I tested the model using questions across five categories: diagnosis and screening, treatment targets, medications, complications, and diabetes statistics. For the most part, the results were excellent. The model answered each question correctly while providing the relevant sources, citations, and page numbers. However, when I asked an out-of-scope question about treating a broken arm, the model still generated an answer. Although it acknowledged that the information wasn't found in the guidelines, it attempted to fill in the gaps with unrelated medical knowledge. In a healthcare application, this kind of hallucination is unacceptable.

To solve this, I added a scope-checking step before generating a response. Using Chroma's similarity search together with a dedicated classification prompt, the application first determines whether a question falls within the scope of the diabetes guidelines. If it doesn't, the model refuses to answer instead of attempting to generate a response. My first implementation was too restrictive and incorrectly rejected valid diabetes questions, but after refining the prompt to better define the application's scope, the balance was much better.

I also improved how sources were displayed. Previously, the same document would appear multiple times if information came from different pages. I updated the application to group pages under a single source, making the citations much cleaner. I also added a few quality-of-life improvements, such as hiding the URL field whenever a source doesn't include one.

By the end of the day, I had a working end-to-end application that I could actually demo. The model answered diabetes-related questions, cited its sources, refused out-of-scope requests, and presented everything through a clean web interface. It took around six to seven hours of work, but it was one of the most rewarding sessions so far. With the foundation complete, my next steps are to expand the knowledge base, improve the UI, and continue adding features to make the application more useful in real clinical scenarios.

Today, I focused on improving the quality of the assistant's retrieval. During testing, I noticed that the model occasionally struggled with follow-up questions because it would retrieve multiple chunks containing nearly identical information. To improve this, I implemented Maximal Marginal Relevance (MMR), which balances relevance with diversity by selecting useful context while avoiding redundant document chunks.

I created a new retrieve_chunks() function that first uses Chroma's similarity_search_with_score() to identify the most relevant candidates. If the best match isn't relevant enough, the assistant refuses to answer. Otherwise, it uses max_marginal_relevance_search() to retrieve a diverse set of highly relevant chunks. I also updated several other functions to integrate this new retrieval pipeline.

Another important improvement was calibrating the similarity score cutoff. I tested the application using a variety of in-scope and out-of-scope questions, recorded their similarity scores, and found that a cutoff of 0.35 provided the best balance. Questions below this threshold consistently retrieved relevant guideline information, while those above it were correctly rejected. After extensive testing, the assistant became much more reliable at knowing when it should—and shouldn't—answer.

  • Developed a polished Streamlit application with live model comparison, an interactive hypothetical risk simulator, low-confidence factor flagging, Docker containerization, and a custom cardiac-inspired user interface.

Time for a new project! I had a great experience building DiaGuide AI because it pushed me to learn new technologies while applying my skills to a field I'm passionate about: healthcare. For my next project, I wanted to challenge myself in a different way. Rather than building another RAG or LangChain application, I wanted to expand my machine learning skills and explore how predictive models can be applied to clinical data.

My new project is CardioLens AI, an explainable heart disease risk prediction platform. I chose heart disease both to explore a different area of medicine and to work more directly with traditional machine learning. I found an existing heart disease prediction tutorial that provides a useful starting point by comparing several classification algorithms on clinical data. I plan to build significantly beyond that foundation by adding features such as risk probabilities, what-if risk comparisons, SHAP explanations, and an interactive web interface.

I started by creating a new project directory and Python environment, installing the initial dependencies, and documenting them in requirements.txt. I also initialized Git and configured .gitignore to exclude my environment and unnecessary local files. One lesson I took from DiaGuide AI was the importance of making meaningful Git commits throughout development. I committed most of that project at once, but this time I want my Git history to actually reflect how the project evolves—and to build better habits for eventually working on larger, collaborative codebases.

Next, I began exploring the Cleveland Heart Disease dataset used by the tutorial. I created my first Jupyter notebook and used Pandas to examine the data. The dataset contains roughly 300 patient records with 13 clinical input features and a target variable, including information such as age, sex, cholesterol, chest pain type, maximum heart rate, and several other clinical measurements.

I checked for missing values, unusual ranges, and potential data quality issues before moving on to some initial exploratory analysis with Seaborn and Matplotlib. I created a correlation heatmap to get an early look at relationships between the variables, with features such as chest pain type (cp) and maximum heart rate (thalach) showing notable relationships with the target. Of course, correlation alone doesn't tell us which features will ultimately be most useful to the model, but it gave me a useful first look at the structure of the dataset.

With the initial exploration complete, my next step is data preprocessing and feature preparation before I begin training and comparing classification models.

While taking another look at the dataset, I noticed a couple of data quality issues that I had initially missed. The ca feature is expected to contain values from 0–3, but some records contained a value of 4. Similarly, thal is expected to use values from 1–3, but there were records containing 0. Since these appear to be undocumented or invalid values rather than meaningful clinical categories, I decided to remove those records during preprocessing rather than risk having the model learn from incorrect data.

I created a preprocessing script that first removes these invalid rows, leaving 296 patient records. I then separated the dataset into X, containing the 13 input features, and y, containing the heart disease target. Using scikit-learn's train_test_split(), I reserved 20% of the data as a test set so the models could later be evaluated on patients they had never seen during training.

Next, I used StandardScaler to standardize the numerical features around a mean of 0 and standard deviation of 1. This is particularly important for scale-sensitive algorithms such as K-Nearest Neighbors and Logistic Regression. To prevent data leakage, I fit the scaler only on the training data and then used that fitted scaler to transform both the training and test sets. I also saved the scaler so that future user inputs can undergo the exact same transformation before being passed to the model.

With preprocessing complete, I moved on to model training. I chose five classification algorithms to compare: Logistic Regression, Random Forest, Gaussian Naive Bayes, K-Nearest Neighbors, and Decision Tree. I trained each model using scikit-learn and saved the fitted models to my models directory.

Saving each model means I won't need to retrain them every time I evaluate the system or launch the Streamlit application. It also gives me the flexibility to compare how different algorithms behave on the same clinical data. With the models trained, my next step is to evaluate their performance and determine which one is the strongest candidate for CardioLens AI.

Today, I focused on evaluating the five classification models I trained previously and determining which one performs best. I created a new Jupyter notebook, loaded the saved test data and models, and used the same fitted scaler from preprocessing to ensure the test features were transformed consistently with the training data.

I then evaluated each model using several scikit-learn metrics, including accuracy, precision, recall, F1-score, and ROC-AUC. Accuracy alone can be misleading in healthcare applications, so I wanted to consider metrics like recall as well—especially because failing to identify a patient who actually has heart disease can be more consequential than producing a false alarm. ROC-AUC also gave me a useful way to compare how well each model distinguishes between the two classes across different classification thresholds.

I organized the results into a DataFrame and created a reusable pipeline that exports the metrics to a CSV file. Later, CardioLens AI can use this file to display a Model Performance Dashboard without recalculating every metric whenever the Streamlit application launches. I also generated a confusion matrix for the top-performing model to visualize its true positives, true negatives, false positives, and false negatives, along with an ROC curve comparing all five models.

Finally, I selected and saved the model with the highest ROC-AUC. In this evaluation, Logistic Regression performed best with an ROC-AUC of 0.888. This model will become the default predictor in CardioLens AI, while users will still have the ability to explore and compare predictions from the other models. With model evaluation complete, I can now start turning these predictions and metrics into an interactive application.

With the models trained and evaluated, my next goal was to make CardioLens AI's predictions more explainable. I created a new Jupyter notebook to experiment with SHAP (SHapley Additive exPlanations), a tool that helps explain how individual features influence a machine learning model's prediction.

I loaded the training and test data, the saved scaler, and my best-performing model, Logistic Regression. Using SHAP, I could examine an individual patient and see which features pushed the model's prediction toward or away from heart disease. For one example patient, thal (thallium stress-test result) had one of the strongest contributions toward a positive prediction, while thalach (maximum heart rate achieved) pushed the prediction in the opposite direction. Along with ca (number of major coronary vessels observed), these were among the most influential features for that particular prediction.

What makes SHAP especially useful is that these explanations can change from patient to patient. Rather than simply telling a user that the model predicts a certain level of risk, CardioLens AI can also provide insight into why the model produced that prediction. It's important to remember that these explanations describe the model's behavior rather than proving medical causation, but they add a valuable layer of transparency to an otherwise difficult-to-interpret prediction.

I finished by generating SHAP visualizations that display how each feature contributes to an individual prediction. My next step is to integrate these explanations into the Streamlit application so every prediction can be accompanied by a clear, patient-specific breakdown of the factors that influenced the model.

Now it's finally time to start building the Streamlit interface for CardioLens AI. I created a new app.py file and began with the basic page structure, including the title, headers, captions, layout, and necessary dependencies. Since the model requires 13 patient features, I organized the input form into three columns to keep everything clean and easy to navigate.

For categorical features such as sex, chest pain type, resting ECG results, and exercise-induced angina, I created dropdown menus that translate the dataset's numerical encodings into understandable labels. Instead of asking someone to enter 0 or 1 for exercise-induced angina, for example, the interface simply displays Yes or No. Streamlit's searchable dropdowns also make it easy to quickly find and select the appropriate option.

For continuous numerical features such as age, cholesterol, resting blood pressure, and maximum heart rate, I used numerical inputs instead. Users can either type a value directly or adjust it using increment and decrement controls. I also added input validation with expected ranges for each feature. If a value falls outside the defined plausibility bounds, the application displays a warning and prevents the prediction from running until the input is corrected.

The interface is still basic for now, but the foundation of the patient input system is complete. My next step is to connect these inputs to the trained model so CardioLens AI can begin generating predictions directly from the Streamlit application.

With the patient input form complete, today's goal was to connect the Streamlit interface to the actual prediction pipeline. I started by loading the best-performing model and saved scaler from my previous model evaluation. Since both artifacts are generated through the reproducible training pipeline I built earlier, the Streamlit application can use the exact same preprocessing and model configuration used during development.

I added a Predict Risk button that collects the 13 patient features and organizes them into a DataFrame in the same order expected by the model. The input is then transformed using the saved scaler before being passed to the model, which returns a predicted probability of heart disease.

To make the result easier to interpret visually, I created three application-defined risk categories: Low (<30%), Moderate (30–70%), and High (≥70%). Each category is displayed with a corresponding color, along with a progress bar representing the model's predicted probability. These thresholds are currently intended as a visualization tool rather than clinically validated risk categories, which will be important to make clear in the final application.

Next, I integrated the SHAP explanation pipeline directly into Streamlit. For every prediction, the application generates a patient-specific SHAP visualization showing which features had the greatest influence on the model's output. I initially ran into a bug where the same visualization appeared after every prediction because I was referencing the wrong saved output. After fixing it, the explanation now updates correctly for each new patient. I also display the top three contributing features alongside their SHAP values, indicating whether each feature pushed the model's prediction toward or away from heart disease.

For now, I'm intentionally keeping the interface relatively simple and focusing on getting the entire prediction pipeline working correctly. One lesson I learned while building DiaGuide AI was that polishing the UI too early meant repeatedly redesigning it whenever I added a new feature. This time, I'm finishing the functionality first and saving the full visual redesign for the end. With prediction and explainability now working end-to-end, CardioLens AI is starting to feel like a complete application.

Today, I wanted to give users more control over CardioLens AI by allowing them to choose which machine learning model generates their prediction. Instead of relying only on Logistic Regression, users can now switch between models such as Random Forest, K-Nearest Neighbors, Naive Bayes, and Decision Tree. When a different model is selected, the application loads the corresponding saved model and updates the prediction, SHAP visualization, and contributing factors accordingly.

Getting this to work was a little more complicated than expected. My original SHAP implementation was designed around Logistic Regression, and the different scikit-learn models didn't all behave identically when passed through the explanation pipeline. Some models prevented the patient input interface from loading, while others produced errors only after clicking Predict Risk. At first, I thought I would need a separate SHAP implementation for every model.

Fortunately, the solution ended up being much simpler. I created a predictive_positive_class wrapper that gives SHAP a consistent callable regardless of which model is selected. The wrapper standardizes the output by returning the model's predicted probability for the positive heart-disease class. With a consistent input/output format, the same SHAP pipeline can now explain predictions from each of the supported models without requiring separate implementations.

I then caught another important edge case involving the what-if comparison feature. If a user generates an original prediction, switches to another model, and then changes patient features for a what-if prediction, the application could accidentally compare results produced by two different models. That wouldn't be a meaningful comparison of the changed patient features. To prevent this, CardioLens AI now detects when the selected model has changed and asks the user to rerun the original prediction before continuing with the comparison.

With that fix, users can now explore multiple machine learning models while keeping the predictions and explanations consistent. It also gave me a good reminder that adding model flexibility isn't just about loading another .pkl file—the entire prediction and explanation pipeline needs to stay synchronized with the model being used.

Now it was time for my favorite part of the project: the UI. With DiaGuide AI, I designed the interface around the look and feel of a continuous glucose monitor, and I wanted CardioLens AI to have the same level of visual identity. This time, however, I built the design around cardiology—using dark reds, softer pinks, rounded components, animations, and Google's Material Symbols throughout the application.

One of my favorite additions was the animated ECG trace beneath the CardioLens AI title. It follows the same concept as the animated glucose graph I created for DiaGuide AI, but now resembles a heart monitor with a moving ECG waveform. I also added hover effects to buttons and consistent rounded icons beside each section heading to make the interface feel more cohesive.

I then redesigned how prediction results are presented. The predicted risk category now appears as a rounded pill badge with a visual indicator corresponding to low, moderate, or high predicted risk. I also reorganized the SHAP explanations into a collapsible Why This Prediction? section, with the feature-impact visualization on one side and the top contributing factors on the other. Rounded containers and badges were added throughout the prediction, SHAP, and what-if comparison sections to keep the design consistent.

I also made several structural changes. Model selection and performance information now live together in the sidebar, keeping model-related controls separate from the patient inputs. I moved the medical disclaimer to an acknowledgment screen shown when the application first launches, so users must confirm that they understand the project's intended use before continuing. This keeps the main interface cleaner while still making the application's limitations clear. Finally, I added a small footer identifying the Cleveland Heart Disease dataset as the source of the underlying data.

There are still a few design details I want to refine, but CardioLens AI finally has the visual identity I had imagined. Tomorrow, I'll focus on the final round of UI polish and getting the interface ready for the finished application.

Today, my goal was to finish the CardioLens AI interface. I started with smaller improvements: centering and enlarging the Predict Risk button, making the patient input fields more symmetrical, replacing bullet points with arrows, improving spacing, and adding hover effects throughout the application. I also renamed What-If Comparison to Hypothetical Comparison, which felt more appropriate for the clinical setting. Each major section now includes a short explanation so users can quickly understand what they're looking at and how to interact with it.

I then focused on making the prediction results easier to interpret. The original and hypothetical predictions now include color-coded probability bars, while the SHAP section was redesigned into a cleaner bar chart showing the six features with the greatest impact on the model's prediction and whether they pushed it higher or lower. I also converted the feature impacts into percentage-point changes in the predicted probability, making the explanations much more intuitive for users who may not be familiar with raw SHAP values. Finally, I replaced abbreviated dataset labels with understandable names so that features such as thal and thalach aren't presented without context.

The Hypothetical Comparison received some of the biggest changes. When users adjust a modifiable feature, the interface now displays its original value alongside the amount it changed. The comparison visualization also shows how the predicted probability moves from the original prediction to the hypothetical one. Decreases are highlighted in green, while increases are shown in red, making the direction and magnitude of the change much easier to understand without constantly referring back to the original inputs.

I continued polishing the overall interface by adding more spacing, rounded containers, and subtle animations when prediction results appear. The patient input form now sits inside its own rounded container as well, helping it match the rest of the visual design.

Finally, I completely redesigned the Model Performance Dashboard in the sidebar. Instead of displaying a large table of every model and metric, users can select a performance metric from a dropdown and view a ranked bar chart comparing the models. I also added a Model Information section with brief explanations of how each algorithm works, which should make the application more approachable for users without a machine learning background. Logistic Regression is currently marked as the recommended default because it achieved the strongest ROC-AUC during my model evaluation, while users can still experiment with any of the five models.

After a lot of small iterations, the CardioLens AI interface finally feels complete. My goal was to take all of the machine learning happening behind the scenes and present it in a way that feels organized, understandable, and visually polished—and I'm really happy with where the final design ended up.

With the interface complete, it was finally time to put CardioLens AI through some end-to-end testing. I created three sample patients designed to represent relatively low, moderate, and high predicted risk. Immediately, something seemed wrong—the results appeared almost completely backwards. The low-risk patient received a high prediction, while the high-risk patient received a low one.

After digging through the pipeline, I discovered that the problem wasn't with SHAP or the interface at all. The target encoding in my dataset was opposite to what my application assumed. My pipeline was interpreting 1 as heart disease being present and 0 as absent, while the dataset I was using encoded the outcome in the opposite direction. I went back to the preprocessing notebook, inverted the binary target so that 1 consistently represented heart disease, and reran the entire downstream pipeline. This meant regenerating the processed data, retraining the models, reevaluating them, and recreating the artifacts used for SHAP. After testing the same three patients again, the predictions finally behaved as expected.

Next, I wanted to make sure the application could run consistently outside of my local environment, so I containerized CardioLens AI with Docker. I created a .dockerignore to exclude development files that weren't necessary at runtime, such as the notebooks and raw training data, and wrote a Dockerfile containing the environment and dependencies required to run the application. After resolving a Python/dependency compatibility issue and rebuilding the image, I launched the container and tested the same three sample patients. Each produced the same results as my local application, confirming that the containerized version was working correctly.

With testing complete, I pushed the finished project to GitHub and deployed the application through Streamlit Community Cloud. This time, deployment worked on the first attempt—a nice improvement over DiaGuide AI, where I ran into several dependency issues during the initial release. And with that, CardioLens AI was officially complete!

Looking back, this project came together much faster than DiaGuide AI. Part of that was because the machine learning pipeline was relatively straightforward, using standard preprocessing techniques such as feature scaling and one-hot encoding to prepare the clinical data for training. A lot of the faster development also came from what I learned during my previous project. Streamlit was no longer new to me, I had a much better understanding of how to structure an application, and I could reference some of the design principles I developed for DiaGuide AI while still giving CardioLens AI its own identity.

More importantly, I feel increasingly comfortable working through the full lifecycle of an applied machine learning project—from exploring healthcare data and preprocessing it, to training and evaluating models, adding explainability, building an interactive application, testing it, containerizing it, and finally deploying it. My next step is to share CardioLens AI with Utah Cardiology and gather feedback from people who actually work in cardiology. I'm excited to see what they think and use their feedback to determine where the project can improve next.
